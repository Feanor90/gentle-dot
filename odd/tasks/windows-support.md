# Windows support for Gentle Dot

Port the desktop app (Tauri 2 shell + Node daemon) to Windows 10/11 x64 without weakening the security model of `docs/design.md` (§4 App channel, Secrets, Integrity; §8).
Delivered in phases on the fork `Feanor90/gentle-dot` (branch `feat/windows-support`, pushed after every task); no PR to `Gentleman-Programming/gentle-dot` until the app works on Windows (L7). Engram mirror: `odd/windows-support/tasks`.

## Specs

- S1 (L1): "Finalmente esto es para mac como comprobarás después de analizar toda la documentación, entonces el proyecto sería si podemos adapatar esto a windows."
- S2 (L2): "redacta un buen plan hermano para implementar esto, ves dejandolo todo en orden en engram par ano perder nada."
- S3 (L3, proposed by the agent, accepted as the working order): deliver in phases — Phase 1 "secure base" (build, app channel, secret store, file privacy, daemon lifecycle, tray, shortcut, installer; no computer control, as on Linux today), Phase 2 voice, Phase 3 computer control.
- S4 (derived from S1 + upstream design §4/§8): every security property the upstream docs claim on macOS/Linux either holds on Windows with an equivalent mechanism and a test, or is documented as a Windows limit in `docs/install.md` and `docs/design.md`, the way S25.7 documents the Linux keyring limit. Never a silent fallback to a weaker store (no secrets in files).
- S5 (derived from S1): existing macOS and Linux behavior is unchanged; every change to shared code (`platform.rs`, `daemon.rs`, `app_channel.rs`, `shell.rs`, `app-channel.ts`, `isolation.ts`, `private-file.ts`) keeps the current tests passing on those targets (Linux checked in Docker with `scripts/package/linux-cargo-check.mjs`; macOS flagged as unverified locally).

- L8 (agent, T1 spike, `odd/spikes/t1-app-channel-windows/`; user: "usa el tema de la seguridad que sea buena"). The fd 3 design works on Windows with every app-channel property of design §4; four identical runs:
  - P1 (connection is the authentication, nothing listens): Rust creates `\\.\pipe\gentle-dot-<128-bit random>` with `FILE_FLAG_FIRST_PIPE_INSTANCE`, 1 instance, `PIPE_REJECT_REMOTE_CLIENTS`, DACL `D:P(A;;GA;;;<user SID>)`, opens the client end itself, and checks `GetNamedPipeClientProcessId` is its own pid (`clientPidIsMe=true`). A second open of the name fails with 231 `ERROR_PIPE_BUSY`. A same-user process that won the race would make the app's own open fail or the pid check fail: fail closed. The name lives only until the app connects.
  - Handover: the client end goes to the daemon as CRT fd 3 through `STARTUPINFOEXW` `lpReserved2` (count, flags `FOPEN|FPIPE`, handles) with `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` = {NUL, log, client}. `new net.Socket({fd: 3})` reads and writes. The client end MUST be opened with `FILE_FLAG_OVERLAPPED`: without it the daemon hung before its first frame (a pending synchronous read blocks writes on the same handle).
  - P3 (no child holds it): grandchildren via `spawn`, `spawnSync`, and `cmd /c` report the handle value invalid (`"valid":false`) and nothing reaches the app; a control child created with plain inheritance does leak (`LEAK control`), so the detector works. Node clears the inherit flag of handles received in `lpReserved2` at startup (libuv `uv_disable_stdio_inheritance`), like Linux's close-on-exec.
  - P4: closing the app's end ends the daemon (`end` -> exit 0).
  - T3 consequences: on Windows `fstatSync(3)` gives `isSocket()=false`, `isFIFO()=false`, `mode=4096` (`S_IFIFO`), `dev=0`, `ino`=handle value. `inheritedAppSocket` must accept that pipe on Windows and its probe cannot use `dev:ino` as identity; a Node probe sees only CRT fds, not handles. The Windows regression test (analog of `app-channel-fd.test.ts`) must check handle-level leaks the way the spike does, with a small native helper. Named-pipe fallback not needed.
